# V3 컴퓨팅 환경 — 결정 사항 및 유의점

> 작성: 2026-10-11
> 대상: V3 (pipe-routing-GNARL) 개발 세션
> 관련: skeleton 레포 `docs/v3_requirements.md`, 본 레포 CLAUDE.md

## 1. 배경 — skeleton에 Colab이 필요 없었던 이유

Walking skeleton은 **학습 없이 최적화 계산만** 수행한다. A\*, rip-up/reroute 등은
규칙이 정해진 결정론적 알고리즘으로, 한 번 실행하면 답이 나온다. 초~분 단위이고
CPU만으로 충분하다.

V3는 성격이 다르다. RL은 **답을 모르는 상태에서 시행착오로 찾는다.**
수십만 step을 반복하며 가중치를 조금씩 갱신해야 하므로 시간 단위의 연속 실행이 필요하다.

**V2 실측 참고치** (MaskablePPO, 150-dim obs, 소규모 격자)

| 항목 | 값 |
|---|---|
| variant 1회 (250K step) | 47.9 ~ 52.3분 |
| 평가 (75 시나리오) | 약 21초 |
| 컴퓨팅 단위 소모 | 1.478 units/시간 (Colab 실측) |
| Round 1 전체 | 약 10시간 |
| Round 2 Phase 2 | 약 13~14시간 |

## 2. Claude 환경으로 학습을 대체할 수 없다

Claude(웹 에이전트 / Claude Code 웹)가 실행되는 환경은 Anthropic 클라우드의
샌드박스 리눅스 VM이다.

- **GPU 없음**
- **세션 종료 시 환경 소멸** — 수 시간짜리 학습을 걸어두고 결과를 받는 용도가 아님
- 파이썬·패키지 설치는 가능하나, 네트워크는 패키지 레지스트리 중심의 allowlist

따라서 **실제 학습은 외부 GPU 환경(Colab 등)에서 수행해야 한다.**

## 4. 유의점 — V3의 병목은 V2와 다를 수 있다

### 4.1 V2에서 GPU 이득이 거의 없었다

**T4 GPU 46분 vs CPU 48분.** 병목이 GPU 연산이 아니라 파이썬 환경 시뮬레이션이었다.
`net_arch=[256,256]` MLP는 연산량이 작아 GPU 전송 오버헤드가 이득을 상쇄했다.

### 4.2 V3에서 달라질 수 있는 요인

**GPU 이득이 커질 수 있음** — GNARL은 그래프 신경망이라 연산량이 V2의 MLP보다 크다.

**환경 쪽 부담이 급증할 수 있음** — 단위 블록 40m × 40m × 10m, 위치 정밀도 10mm.
단순 조밀 격자로는 셀 수가 수십억 단위가 된다. 희소 표현·계층 구조를 쓰더라도
V2의 소규모 격자와는 비교할 수 없는 메모리·CPU 부담이 예상된다.

**→ V3의 병목이 GPU인지 CPU·메모리인지 현재 불확실하다.**
이것이 정해져야 "Colab Pro로 충분한가, 외부 GPU 임대가 필요한가,
아니면 맵 해상도·블록 크기를 재조정해야 하는가"에 답할 수 있다.

## 5. 설계 단계에 박아둘 측정 지점

V2에서 소요 시간 추정이 반복적으로 빗나갔다 (3~4시간 추정 → 실제 10시간).
그 결과 Colab Pro 구독 시점이 뒤늦어졌고 작업이 여러 세션으로 쪼개졌다.

V3는 환경 규모가 훨씬 크므로, **추정이 아니라 실측을 설계 초기에 확보한다.**

### 필수 측정 항목 (학습 본격화 이전)

- [ ] 학습 1회(목표 step 수)의 벽시계 시간
- [ ] 피크 메모리 사용량 (시스템 RAM / GPU RAM 각각)
- [ ] GPU 유무에 따른 속도 차이 — V2처럼 차이가 작으면 GPU 비용이 낭비
- [ ] 환경 step 1회의 소요 시간 (환경이 병목인지 판별)
- [ ] 평가 1회(시나리오 세트 전체)의 소요 시간

### 기록 원칙

- 측정값은 PROGRESS.md에 의사결정으로 기록
- variant별 시간·GPU 종류를 캐시 JSON에 함께 저장 (V2 §9 리포트 방식 계승)
- 학습 시작 전후로 컴퓨팅 단위 잔량을 수동 기록 (API로 조회 불가)

## 6. V2에서 계승할 운영 장치

V2 Round 1~2에서 비용을 크게 아낀 패턴들. V3에도 적용 가치가 있다.

**작게 확인하고 크게 투자한다** — Round 2 Phase 1에서 6 variant(7.4 units)로
극값 스크리닝을 먼저 돌려 w1 축을 탈락시켰고, grid가 36개에서 9개로 줄었다.

**노이즈 폭을 먼저 측정한다** — 동일 조합 3-seed 반복(2.5 units)으로
측정 한계가 0.0135임을 확인했다. 그보다 작은 차이는 순위로 쓸 수 없다.
이 확인 없이 Stage 2(59 units)에 투입했다면 전부 노이즈였다.

**variant 단위 캐시 + 체크포인트 저장** — 세션이 끊겨도 완료분이 보존된다.
V2에서 이것이 없어 7시간 분량을 한 번 소실했다.

**파라미터가 소비처까지 실제로 도달하는지 테스트한다** — V2에서 seed 전달 누락과
w1/w2/w3 배선 누락이 각각 발생했다. spec에 정의된 값이 코드에 연결되지 않은 채
실험이 도는 사고를 막는 장치가 필요하다.
